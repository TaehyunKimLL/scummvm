### New Breakage / Regressions Introduced by Fix Round 1

#### Critical

1. **N1 — Heap / global buffer over-read in `CharsetRendererV2` for `U+0080..U+00FF` because `_numChars` is `0`**
   - **Locations:** [charset.cpp:962-963](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/charset.cpp#L962-L963), [charset.cpp:1053-1054](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/charset.cpp#L1053-L1054), [charset-fontdata.cpp:705-782](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/charset-fontdata.cpp#L705-L782), [charset.h:286](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/charset.h#L286)
   - **Scenario:** `CharsetRendererV2` inherits `printChar()` and `drawChar()` from `CharsetRendererV3` and overrides `setCurID()` to a no-op (`charset.h:286`). Its constructor (`charset-fontdata.cpp:705-782`) never initializes `_numChars`, leaving it at `0` from `CharsetRendererCommon` ([charset.cpp:356](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/charset.cpp#L356)). For Korean v1/v2 targets (`default:` branch), `_fontPtr` points to the 128-glyph (1,024-byte) `englishCharsetDataV2` (v2) or a heap-allocated `new byte[1024]` copy (v1, `charset-fontdata.cpp:771`). When `printChar()` or `drawChar()` is called with any `chr` in `0x80..0xFF` (e.g., a stray high byte converted to `U+0080..U+00FF` or a Latin-1 character in MM/Zak), `is2byte` is `0` and the new guard `chr >= (_numChars ? _numChars : 256)` evaluates to `chr >= 256`, which is **false**. Execution proceeds to `charPtr = _fontPtr + chr * 8`, reading up to 1,024 bytes past the end of the 1,024-byte font buffer (heap buffer over-read on SCUMM v1; `.rodata` over-read on SCUMM v2).
   - **Fix:** Initialize `_numChars` in `CharsetRendererV2::CharsetRendererV2` to match the backing table size (`sizeof(englishCharsetDataV2) / 8` = `128`, or `sizeof(russianCharsetDataV2) / 8` = `256` on the Russian non-replacement branch).

2. **N2 — `legacyCp949Resource()` rejects valid legacy CP949 resources containing `0xFE` escapes (`0xFE 0x01` / `0xFE 0x08`)**
   - **Location:** [korean_text.cpp:375-388](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/korean_text.cpp#L375-L388)
   - **Scenario:** `legacyCp949Resource()` skips `0xFF` escapes (`if (*p == 0xFF)`, line 376), but does not skip valid `0xFE` text escapes (`0xFE 0x01`/`0x02`/`0x03`/`0x08`). After stepping past `0xFE` (line 385), the next iteration sees `0x01`/`0x08 < 0x20` at line 382 and returns `false`. As noted in [P6a-fixes.md:13](file:///home/thkim/work/tmp/scummvm-review-p6a/docs/korean/plans/P6a-fixes.md#L13), real Korean bundles contain hundreds of `0xFE 0x01` and `0xFE 0x08` escapes (e.g., MI2: 318 + 64; MI1 UTE: 18 + 17). Any legacy CP949 save containing such a `rtVerb`, `rtString`, or `rtObjectName` resource (e.g. `"한글\xfe\x08다음\0"`) is skipped by `convertLoadedText()` and remains raw CP949 in memory, rendering as mojibake/refusal glyphs.
   - *(Related edge case in [korean_text.cpp:397-407](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/korean_text.cpp#L397-L407)):* `legacyCp949Buffer()` skips conversion when `pairs == 0`, so a legacy CP949 `_charsetBuffer` with no Hangul but a single-byte charset glyph (e.g. `0xFA` in `"St.\xfaKitts"`) is left unconverted and `nextCJKChar()` renders `'?'` instead of glyph `0xFA`; its `pairs` loop also doesn't skip `0xFF` escape arguments.
   - **Fix:** In `legacyCp949Resource()`, handle `textEscape(p, end)` (both `0xFF` and `0xFE {1,2,3,8}`) before the `< 0x20` rejection. In `legacyCp949Buffer()` (`_charsetBuffer` is always text, never binary), skip escapes in the scan and convert whenever any byte `>= 0x80` (outside escapes) is present.

3. **N3 — `toEngineText()` breaks idempotence for 2-byte UTF-8 characters `> U+00FF` between `knownUtf8 = true` and `knownUtf8 = false`, and `tolerantUtf8()` splits them into garbage Latin-1**
   - **Locations:** [korean_text.cpp:275-287](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/korean_text.cpp#L275-L287), [korean_text.cpp:305-322](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/korean_text.cpp#L305-L322), [string.cpp:2507-2526](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/string.cpp#L2507-L2526)
   - **Scenario:** Suppose a UTF-8 `.trs` translation contains a 2-byte UTF-8 character above `U+00FF` (e.g., `ī` = `U+012B` = `C4 AB`):
     1. On initial load (`loadPtrToResource()` -> `translateText()`), the bundle match calls `copyTranslatedText(..., knownUtf8 = true)` (`string.cpp:2507`). `utf8Valid(src, end, true)` accepts `C4 AB` and stores it in the resource.
     2. When that resource is later passed through `translateText()` on draw, it misses the bundle lookup and falls through to `copyTranslatedText(..., knownUtf8 = false)` (`string.cpp:2526`).
     3. Now `textIsUtf8()` (`allowWide = false`) rejects `C4 AB`. Without Hangul (or when `utf8HangulCount <= cp949PairCount`), `toEngineText()` routes it to `cp949ToUtf8()`, **corrupting `ī` (`C4 AB`) into Hangul `카` (`EC B9 B4`)**. With Hangul (`utf8HangulCount > cp949PairCount`), `tolerantUtf8(..., allowWide = false)` enters the `(!allowWide && len == 2 && cp > 0xFF)` branch and executes `appendUtf8(*p, out); p++;`, **splitting `C4 AB` into two garbage Latin-1 characters `U+00C4 U+00AB` (`Ä«`)**.
   - *(Related edge case in [korean_text.cpp:315-321](file:///home/thkim/work/tmp/scummvm-review-p6a/engines/scumm/korean_text.cpp#L315-L321)):* Many common 3-byte UTF-8 Hangul syllables contain continuation-byte pairs that are also valid KS X 1001 pairs (e.g. `복` = `EB B3 B5` where `B3 B5` = `논`; `건` = `EA B1 B4` where `B1 B4` = `거`), so a 1-syllable UTF-8 string with a stray byte (`"복\xfa"`) gets `utf8HangulCount == 1 == cp949PairCount`, fails `>`, and is misrouted to `cp949ToUtf8()`.
   - **Fix:** Make `knownUtf8 = true` and `knownUtf8 = false` agree on `U+0100..U+07FF` (either normalize/replace unrenderable `len == 2 && cp > 0xFF` on `knownUtf8 = true`, or have `tolerantUtf8()` preserve valid `len == 2` sequences instead of splitting them byte-by-byte), and avoid double-counting bytes inside valid 3-byte UTF-8 Hangul in `cp949PairCount`.
